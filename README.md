# Помощник по ВКР

Веб-приложение для студентов бакалавриата Высшей школы бизнеса МГУ (38.03.02 Менеджмент). Оно **не пишет текст ВКР**, а берёт на себя рутину: сроки, план-график, чек-листы требований, список литературы, ссылки в тексте, нумерацию рисунков и таблиц, реестр допущений и рисков, шаблон Word.

Единственный источник требований — Программа ГИА ВШБ МГУ на 2026-2027 учебный год. Рядом с каждым требованием в интерфейсе указан номер пункта программы, чтобы его можно было сверить с оригиналом.

У каждого студента свой аккаунт, и он видит только свои данные. Файлы ВКР на сервер не загружаются: хранятся только отметки и справочные данные.

## Как запустить проект

Понадобятся три бесплатных аккаунта: **GitHub** (хранит код), **Supabase** (база данных и вход по почте) и **Vercel** (размещает сайт). Программировать не нужно.

### Шаг 1. База данных в Supabase

1. Зайдите на [supabase.com](https://supabase.com), зарегистрируйтесь и нажмите **New project**.
2. Придумайте название и пароль базы данных (пароль сохраните у себя), выберите ближайший регион, нажмите **Create new project** и подождите пару минут.
3. В меню слева откройте **SQL Editor** и нажмите **New query**.
4. Откройте в этом репозитории файл `supabase/migrations/20261117000000_init.sql`, скопируйте его содержимое целиком, вставьте в редактор и нажмите **Run**. Должно появиться сообщение `Success. No rows returned`.
5. Проверьте результат: в меню слева откройте **Table Editor**. Там должно быть 11 таблиц, у каждой отметка о включённом RLS.

Миграцию нужно выполнить один раз. Она создаёт таблицы и включает на каждой Row Level Security с правилом «пользователь видит только свои строки».

### Шаг 2. Ключи Supabase

1. В Supabase откройте **Project Settings** (значок шестерёнки) → **API** (или кнопку **Connect** вверху страницы).
2. Скопируйте два значения:
   - **Project URL** — адрес вида `https://xxxxxxxx.supabase.co`;
   - публичный ключ — он называется **publishable** или **anon public**.

Ключ с названием **service_role** или **secret** не нужен. Никуда его не вставляйте и никому не показывайте: он даёт полный доступ к базе в обход защиты.

### Шаг 3. Размещение на Vercel

1. Зайдите на [vercel.com](https://vercel.com) и войдите через аккаунт GitHub.
2. Нажмите **Add New… → Project** и выберите этот репозиторий, затем **Import**.
3. Раскройте раздел **Environment Variables** и добавьте две переменные:

   | Name | Value |
   |---|---|
   | `NEXT_PUBLIC_SUPABASE_URL` | Project URL из шага 2 |
   | `NEXT_PUBLIC_SUPABASE_ANON_KEY` | публичный ключ из шага 2 |

4. Нажмите **Deploy**. Через минуту-две Vercel покажет адрес сайта вида `https://название.vercel.app`.

Если вы добавили или изменили переменные уже после размещения, откройте **Deployments**, нажмите на три точки у последней сборки и выберите **Redeploy** — иначе изменения не подействуют.

### Шаг 4. Адрес сайта в Supabase

Чтобы ссылки из писем (подтверждение почты, смена пароля) вели на ваш сайт:

1. В Supabase откройте **Authentication → URL Configuration**.
2. В поле **Site URL** вставьте адрес сайта из шага 3.
3. В **Redirect URLs** добавьте тот же адрес со звёздочками на конце: `https://название.vercel.app/**`.
4. Сохраните.

### Шаг 5. Письма с подтверждением

По умолчанию Supabase просит подтвердить почту и отправляет письма через собственный сервис с жёстким ограничением: всего несколько писем в час. Для группы студентов этого не хватит. Есть два варианта:

- **Проще:** в **Authentication → Sign In / Providers → Email** выключить **Confirm email**. Тогда студент входит сразу после регистрации. Минус: можно зарегистрироваться на чужой адрес, и восстановление пароля по почте будет упираться в то же ограничение.
- **Надёжнее:** подключить свой почтовый сервис в **Authentication → Emails → SMTP Settings**.

### Шаг 6. Проверка

Откройте сайт, зарегистрируйтесь, заполните профиль. Затем зарегистрируйте второго пользователя с другой почтой и убедитесь, что он не видит данные первого.

Ту же проверку можно сделать автоматически, на всех 11 таблицах сразу:

1. В Supabase откройте **Authentication → Users → Add user → Create new user** и создайте двух тестовых пользователей (поставьте галочку **Auto Confirm User**).
2. На своём компьютере скопируйте `.env.example` в `.env.local` и впишите адрес проекта, публичный ключ и почты с паролями двух тестовых пользователей.
3. Выполните `npm run check:rls-live`. Скрипт создаст от имени первого пользователя по строке в каждой таблице, попробует прочитать, изменить, удалить их и подделать от имени второго, проверит доступ без входа и уберёт за собой тестовые строки. В конце будет итог: «изоляция данных работает» или список нарушений.

## Переменные окружения

| Переменная | Что это | Где взять |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | адрес проекта Supabase | Project Settings → API |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | публичный ключ | Project Settings → API Keys |
| `NEXT_PUBLIC_DEMO_MODE` | необязательная; `1` включает демо-режим | задаётся вручную |

Секреты хранятся только в переменных окружения. Файл `.env.local` в репозиторий не попадает (он указан в `.gitignore`); образец лежит в `.env.example`.

Публичный ключ попадает в браузер — это нормально: данные защищает Row Level Security в базе, а не секретность этого ключа.

**Демо-режим.** Если ключи Supabase не заданы, а `NEXT_PUBLIC_DEMO_MODE=1`, приложение работает без базы: данные хранятся только в браузере, пароль не спрашивается. Режим нужен, чтобы посмотреть приложение до настройки Supabase. На рабочем сайте его не включайте.

## Как обновить требования на следующий год

Все требования программы лежат в одном файле: `src/requirements/gia-2026-2027.ts`. Там сроки, ограничения объёма, структура, правила оформления, тексты форм и заявлений. У каждого правила есть поле `clause` с номером пункта.

1. Скопируйте файл под новым именем, например `gia-2027-2028.ts`.
2. Исправьте в копии всё, что изменилось в новой программе: даты в `DEADLINES`, год защиты в `PROGRAMME.defenceYear`, ограничения в `LIMITS`, тексты форм, номера пунктов.
3. В файле `src/requirements/index.ts` поменяйте одну строку, чтобы она указывала на новый файл.
4. Сохраните изменения в GitHub — Vercel пересоберёт сайт сам.

Файлы можно править прямо на сайте GitHub: откройте файл и нажмите значок карандаша.

Если в программе изменился формат записей списка литературы или ссылок, правьте `src/lib/bibliography.ts` и `src/lib/citations.ts`, а эталонные строки — в `tests/bibliography.test.ts`.

## Спорные места программы

Там, где программа неоднозначна, приложение не угадывает, а показывает примечание:

- **Срок 15 апреля.** В Прил. 8 указан 2026 год; по порядку этапов это 2027. В приложении стоит 15.04.2027 с пометкой.
- **Размер листа.** В Прил. 7 написано «270 x 297 мм»; используется стандартный A4, 210 x 297 мм.
- **Отступ первой строки.** Указано «1,5» без единицы измерения; по умолчанию 1,5 см, значение можно изменить.
- **Название списка литературы.** В Прил. 5 — «Список использованной литературы», в п. 2.6 и Прил. 7 — «Список литературы»; используется второе.
- **Положение номера страницы** не задано; в шаблоне он внизу по центру.
- **Код EDN и ссылка на двух авторов.** Примеров в программе нет; запись формируется как `EDN: КОД`, а фамилии двух авторов перечисляются через запятую.

Все эти вопросы стоит уточнить у научного руководителя или в учебном отделе.

## Для разработчиков

Стек: Next.js (App Router), TypeScript, Tailwind CSS, Supabase (Auth, Postgres, RLS), библиотека `docx`. Приложение целиком работает в браузере; файлы Word собираются на стороне пользователя.

```bash
npm install
```

```bash
cp .env.example .env.local
```

```bash
npm run dev
```

```bash
npm run dev:demo
```

```bash
npm test
```

```bash
npm run test:rls
```

`npm run dev:demo` запускает приложение в демо-режиме без Supabase.

Тесты (`tests/`):

- `bibliography.test.ts` — записи списка литературы сверяются с примерами Приложения 6 символ в символ; порядок, буквы после года, обязательные поля;
- `citations.test.ts` — ссылки в тексте по Прил. 7, пп. 13–17;
- `numbering.test.ts` — нумерация рисунков и таблиц, пересчёт после удаления и перестановки;
- `docx.test.ts` — оформление шаблона, тексты заявлений, анонимный экземпляр, план-график;
- `rls.test.ts` — миграция выполняется в Postgres внутри процесса (PGlite); два тестовых пользователя не могут прочитать, изменить или подменить строки друг друга ни в одной таблице. Docker и аккаунт Supabase для этого теста не нужны.

Структура:

```
src/requirements/     требования программы (единственный источник)
src/lib/              генераторы записей, ссылок, нумерации, файлов Word; доступ к данным
src/components/       общие элементы интерфейса
src/app/(auth)/       вход, регистрация, восстановление пароля
src/app/(app)/        страницы разделов
supabase/migrations/  схема базы данных и политики RLS
tests/                тесты
```

## Чего в приложении нет

- генерации текста с помощью ИИ;
- хранения файлов ВКР на сервере;
- автоматической проверки доступности ссылок — студент проверяет каждую сам и ставит отметку «ссылка проверена вручную».
